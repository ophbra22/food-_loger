# Biteflow לנייד (Android ו־iPhone)

אפליקציית React Native (Expo SDK 57, TypeScript) שמתחברת לשרת ה־FastAPI הקיים של FoodLogger.
האתר והנתונים הקיימים לא השתנו; האפליקציה משתמשת באותם חשבונות ובאותו יומן.

עדכון 13 באוקטובר: ניתוח כמה מאכלים בתמונה, עריכת הכמויות ואישור ערכי USDA
מופיעים במסך Orbit החדש. השירות פועל בשרת הקיים באמצעות Google Free Tier,
ללא תלות במחשב הביתי. מצב הבנייה, ההעלאה והבדיקות מתועד ב־[דוח הגרסה](docs/MEAL_ANALYSIS_RELEASE.md).

מה יש באפליקציה: כניסה, הרשמה ושחזור חשבון עם קוד שחזור; מסך יומי עם חוגת 24 שעות,
סיכום קלוריות ואבות מזון ורשימת הארוחות; הוספת ארוחה מצילום, מתמונה, מברקוד, מהקטלוג או בהזנה ידנית;
מסך בדיקה ואישור לפני שמירה; פרטי ארוחה ומחיקה; מעבר בין ימים; ייצוא CSV דרך תפריט השיתוף של המכשיר;
הגדרות שפה (עברית / English), יציאה ומחיקת חשבון לאחר אימות הסיסמה ואישור מפורש.

צילומי מסך בשתי השפות: [docs/screenshots](docs/screenshots). דוח בדיקות: [docs/TEST_REPORT.md](docs/TEST_REPORT.md).

שם האפליקציה עודכן ל־Biteflow במסכים, בהרשאות ובשם המוצג במכשיר. מזהי ההתקנה והאחסון נשמרו כדי להמשיך להשתמש באותה התקנה ובנתונים הקיימים. צילומי מסך היסטוריים עשויים עדיין להציג את השם הקודם.

## מה צריך להתקין

| כלי | למה | הערה |
|---|---|---|
| Node.js 22.13 ומעלה | הרצת Expo | נבדק עם Node 26 |
| Xcode | בנייה ל־iPhone ולסימולטור | Mac בלבד. נבדק עם Xcode 27 |
| Android Studio | בנייה לאנדרואיד ואמולטור | כולל את ה־JDK הנדרש |
| Python 3.11 או 3.12 | הרצת השרת מקומית | כמו בפרויקט המקורי |

## 1. הפעלת השרת

מתיקיית השורש של המאגר:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -e ".[ml,dev]"
foodlogger download-model
foodlogger
```

התוספת `ml` משמשת את מסלול הזיהוי הישן. מסלול ניתוח הארוחה החדש דורש הגדרת
ספק התמונה בשרת כמפורט ב־[הוראות הניתוח](../docs/MEAL_ANALYSIS.md); מפתח Google
נשמר בשרת בלבד. היומן, הקטלוג והברקודים אינם דורשים את מפתח התמונה.

לבדיקה מטלפון אמיתי באותה רשת Wi‑Fi יש להאזין בכל הכתובות:

```bash
foodlogger --host 0.0.0.0
```

## 2. כתובת השרת באפליקציה

מעתיקים את `.env.example` ל־`.env` בתיקיית `mobile` וקובעים את `EXPO_PUBLIC_API_URL`:

| היכן רצה האפליקציה | הכתובת |
|---|---|
| סימולטור iOS באותו Mac | `http://localhost:8000` |
| אמולטור Android | `http://10.0.2.2:8000` |
| טלפון אמיתי באותה רשת | `http://<כתובת ה־IP של המחשב>:8000` |
| השרת שפורסם ב־Render | `https://<שם השירות>.onrender.com` |

חשוב: בטלפון, `localhost` הוא הטלפון עצמו ולא המחשב. את כתובת ה־IP של המחשב ב־Mac אפשר לקבל כך:

```bash
ipconfig getifaddr en0
```

ב־11.10.2026 הכתובת שנבדקה כאן הייתה `192.168.68.61`; יש להריץ את הפקודה מחדש בכל רשת.
בטלפון פותחים תחילה `http://<IP>:8000/api/health` בדפדפן, ואז מזינים את אותה כתובת ללא `/api/health` בשדה ״שרת״ באפליקציה ולוחצים ״בדיקת חיבור״.

הכתובת נצרבת באפליקציה בזמן הבנייה. בקובץ הזה יש רק כתובת; אין לשים בו סיסמאות, מפתחות או כתובת של מסד נתונים.
כשלא הוגדר דבר, גרסת פיתוח פונה אוטומטית למחשב המקומי (`localhost` ב־iOS, `10.0.2.2` באנדרואיד).

בגרסאות בדיקה (גרסת פיתוח, או בנייה עם `EXPO_PUBLIC_ALLOW_SERVER_OVERRIDE=1`) אפשר להחליף שרת מתוך האפליקציה:
במסך הכניסה מופיעה שורת "שרת" בתחתית, והיא קיימת גם במסך ההגדרות. כך כתובת שגויה לא נועלת את הבודק בחוץ.

## 3. הרצה בסימולטור ובאמולטור

```bash
cd mobile
npm install
```

iPhone (סימולטור):

```bash
npm run ios
```

Android (אמולטור פתוח או מכשיר מחובר ב־USB):

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
npm run android
```

הפקודות בונות "גרסת פיתוח" (development build) ומתקינות אותה. לאחר ההתקנה הראשונה מספיק להריץ:

```bash
npm start
```

אם `pod install` נכשל עם שגיאת `Unicode Normalization`, יש להריץ קודם `export LANG=en_US.UTF-8`.

### למה לא Expo Go

Expo Go מתאים להצצה ראשונה בלבד (`npm run start:go`). הוא מאפס את כיוון הקריאה בכל פתיחה,
ולכן החלפת עברית/אנגלית והמצלמה נבדקות רק בגרסת פיתוח או בגרסה מותקנת.

## 5. קובץ APK לאנדרואיד

ה־APK המעודכן נוצר ונבדק בהתקנה ובהפעלה על האמולטור ב־11.10.2026:
`mobile/dist/FoodLogger-test.apk`. הוא פועל ללא Metro, עם כתובת ברירת מחדל `http://192.168.68.61:8000` ועם אפשרות להחליף אותה במסך הכניסה או בהגדרות.

לבנייה חוזרת מהשורש:

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$ANDROID_HOME/platform-tools:$PATH"
export EXPO_PUBLIC_API_URL="http://$(ipconfig getifaddr en0):8000"
export EXPO_PUBLIC_ALLOW_SERVER_OVERRIDE=1
cd mobile
npx expo prebuild --platform android
cd android
./gradlew assembleRelease
```

התוצר: `mobile/android/app/build/outputs/apk/release/app-release.apk`.
להתקנת התוצר שסופק, משורש המאגר:

```bash
adb devices -l
adb install -r mobile/dist/FoodLogger-test.apk
```

בטלפון מפעילים Developer options ו־USB debugging ומאשרים את המחשב על מסך הטלפון, לפי [הנחיות Android](https://developer.android.com/studio/run/device).
אפשר גם להעביר את ה־APK לטלפון ולפתוח אותו, ולאשר התקנה מהמקור שנבחר אם Android מבקש.
הקובץ חתום במפתח בדיקה, ללא תהליך הפצה בחנות. במקרה של מחסור במקום יש לפנות מקום; הסרת האפליקציה מוחקת את המידע המקומי, ולכן אין לעשות זאת אם יש טיוטה שצריך לשמור.

## 6. iPhone אמיתי וסימולטור

הגדרות המצלמה, התמונות, הרשת המקומית וה־bundle ID נמצאות ב־`app.config.ts`. בוצעה בניית Debug לסימולטור, התקנה והפעלה עם Keychain תקין. אין קובץ IPA למכשיר פיזי.
תוצר הסימולטור נמצא ב־`mobile/dist/FoodLogger-simulator.app` ומתועד בדוח הבדיקות; הוא אינו ניתן להתקנה על iPhone אמיתי, וגרסת הפיתוח דורשת Metro (`npm start`). אין לבטל חתימה עם `CODE_SIGNING_ALLOWED=NO`: בניסוי כאן זה מנע גישה תקינה ל־Keychain.

להרצה על iPhone מחובר:

1. מחברים בכבל, מאשרים Trust בטלפון ומוסיפים Apple Account ב־Xcode Settings → Accounts.
2. מפעילים Developer Mode בטלפון דרך Settings → Privacy & Security, ומבצעים את ההפעלה מחדש והאישור ש־iOS דורש. [הנחיות Apple](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device).
3. משורש המאגר מריצים:

```bash
export LANG=en_US.UTF-8
export EXPO_PUBLIC_API_URL="http://$(ipconfig getifaddr en0):8000"
export EXPO_PUBLIC_ALLOW_SERVER_OVERRIDE=1
cd mobile
npx expo prebuild --platform ios
open ios/FoodLogger.xcworkspace
```

4. ב־Xcode בוחרים את יעד FoodLogger, את המכשיר המחובר, ואת Team תחת Signing & Capabilities; מפעילים Automatically manage signing ומוודאים שה־bundle identifier פנוי לצוות. אם Apple מבקשת אישור לחשבון או הסכם, בעל החשבון משלים אותו.
5. מריצים `npx expo run:ios --device`. לבנייה עתידית משתמשים שוב באותן משתני סביבה. להפעלות פיתוח נוספות משאירים `npm start` רץ ונגיש ברשת.

חשבון Personal Team מאפשר בדיקה אישית ללא חברות בתשלום; פרופילי ההתקנה פגים אחרי שבעה ימים ואז בונים ומתקינים מחדש. הפצה באמצעות TestFlight או Ad Hoc דורשת חברות מתאימה בתוכנית Apple וחתימה/פרופילים מתאימים. [דרישות Apple שנבדקו ב־11.10.2026](https://developer.apple.com/help/account/basics/about-your-developer-account/), [הרצה מקומית ב־Expo](https://docs.expo.dev/guides/local-app-development/).

כאן לא נמצא iPhone זמין. נמצאה זהות Apple Distribution בלבד, ואין בכך הוכחה שחתימת פיתוח למכשיר תצליח. לא הופעל שירות בתשלום ולא בוצע פרסום.

## פתרון תקלות חיבור והרשאות

- המחשב והטלפון צריכים להיות באותה רשת שאינה מבודדת לקוחות. מריצים את השרת עם `--host 0.0.0.0`; בודקים שה־Mac אינו ישן ושחומת האש מאפשרת את תהליך Python. אין צורך לפתוח פורט בנתב לאינטרנט.
- אם בדיקת הכתובת בדפדפן נכשלת, בודקים IP עדכני, פורט 8000, Wi-Fi, VPN וחסימת רשת אורחים. אם היא עובדת ובדיקת האפליקציה נכשלת, בודקים את הכתובת שהוזנה והרשאת Local Network ב־iOS.
- אמולטור Android משתמש ב־`10.0.2.2` כדי להגיע למחשב; טלפון אמיתי משתמש בכתובת ה־LAN. גרסת ה־APK כוללת אפשרות לשנות שרת בלי לבנות מחדש.
- אחרי דחיית מצלמה/תמונות, פותחים את הרשאות Biteflow בהגדרות המכשיר ומאשרים את ההרשאה הנדרשת. לא צריך לאשר מיקרופון.
- בזמן בדיקת מקלדות: ב־Device Hub בוחרים Device → Keyboard → Toggle Software Keyboard; ב־Android מפעילים Show virtual keyboard גם כאשר מקלדת פיזית מחוברת.

## מה חייבים לבדוק על מכשיר אמיתי

בסימולטור ובאמולטור אין מצלמה אמיתית. על טלפון יש לבדוק:

1. "צילום": צילום מנה, קבלת הצעות, אישור ושמירה.
2. "סריקת ברקוד": אישור הרשאת מצלמה, סריקה חיה של מוצר ארוז, ותאורה (כפתור הברק).
3. דחיית הרשאת המצלמה ואז פתיחת ההגדרות מהכפתור שבמסך.
4. הקלדה כשהמקלדת פתוחה במסך "בדיקה ואישור": השדה שבמיקוד וכפתור השמירה צריכים להישאר גלויים.
5. בחירת צילום אוכל אמיתי מהספרייה; רושמים בנפרד הצלחת העלאה/עיבוד ואת נכונות הזיהוי.
6. ייצוא CSV ושיתוף לאפליקציה אחרת (אימייל, קבצים), בדיקת תוכן הקובץ.
7. הגדלת טקסט, מעבר לרקע וחזרה, ניתוק וחיבור רשת, שמירה חוזרת ללא כפילות.
8. מחיקת חשבון בדיקה בלבד; אימות שהחיבור במכשיר נוסף נשלל.

## מבנה הקוד

```text
mobile/
  app.config.ts        הגדרות האפליקציה, הרשאות ותוספים
  eas.json             פרופילי בנייה: development, preview, production
  .env.example         דוגמה לכתובת השרת
  src/
    app/               מסכים וניווט (Expo Router)
    components/        רכיבי ממשק משותפים: כפתור, שדה, חוגת היום, שורת ארוחה
    theme/             מערכת העיצוב: צבעים, טיפוגרפיה, ריווחים
    api/               תקשורת עם השרת, סוגי נתונים, מיפוי שגיאות להודעות
    auth/              חיבור לחשבון ושמירת האסימון ב־Keychain / Keystore
    data/              יומן, טיוטות ושמירה ללא כפילויות
    domain/            לוגיקה עסקית: ולידציה, חישובי מנות, תאריכים, גיאומטריית החוגה
    i18n/              תרגומים (locales/en.ts, locales/he.ts), עיצוב מספרים ותאריכים, כיוון
    storage/           אחסון מקומי מופרד לפי חשבון
```

## שפה וכיוון

- בהפעלה הראשונה השפה נקבעת לפי שפת המכשיר: עברית למכשיר בעברית, אנגלית לכל השאר.
- החלפת שפה בהגדרות נשמרת בין הפעלות. האפליקציה נטענת מחדש פעם אחת כדי להפוך את כיוון הקריאה; טיוטה שלא נשמרה נשארת.
- החוגה, שעות, ברקודים, שם המשתמש, קוד השחזור וכתובות נשארים משמאל לימין גם בעברית.
- שמות מזונות מהקטלוג מתורגמים לפי המזהה שלהם. שמות מוצרים מ־Open Food Facts מוצגים כפי שהתקבלו ואינם מתורגמים.

## אבטחה ונתונים

- האפליקציה נכנסת כ"לקוח נייד": השרת מחזיר אסימון חיבור אטום במקום עוגייה, והוא נשמר ב־Keychain (iOS) או ב־Keystore (Android).
- האתר ממשיך לעבוד בדיוק כמו קודם, עם עוגיית HttpOnly והגנת CSRF.
- כל שמירת ארוחה נשלחת עם מפתח ייחודי (`Idempotency-Key`), כך שניסיון חוזר אחרי תקלה ברשת לא יוצר ארוחה כפולה.
- טיוטה נשמרת בטלפון עד שהשרת מאשר את השמירה. טיוטות ומטמון מופרדים לפי חשבון ונמחקים ביציאה מהחשבון.
- מחיקת חשבון דורשת סיסמה נוכחית ואישור. השרת מוחק את החשבון, הארוחות וכל החיבורים בעסקה אחת; האפליקציה מנקה אסימון, טיוטה, מטמון וקובצי CSV ותמונות זמניות במטמון האפליקציה. עותק שכבר שותף לאפליקציה אחרת אינו בשליטת Biteflow.
- SQLite מוסיף אוטומטית trigger המונע שמירה לחשבון שכבר נמחק. PostgreSQL משתמש במפתחות הזרים הקיימים; אין migration ידני חדש.
- ערך תזונתי חסר נשאר חסר ואינו מוצג כאפס.
- תוצאת זיהוי תמונה היא הצעה בלבד: בוחרים את המזון ומזינים כמות לפני שמירה. האפליקציה אינה מסיקה משקל מתמונה.
