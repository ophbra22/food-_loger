## Functional behavior

- Manual calorie, protein, carbs, fat, water and optional target-weight values can each be unset. Goal changes append owner revisions with expected-version concurrency. Effective local date defaults to today; changing historical dates requires explicit acknowledgement. A tomorrow revision preserves yesterday. Same-date changes retain earlier revisions. The optional automatic estimator was not added.
- `GET/PUT /api/goals` and `GET /api/daily-summary?date=` are gated by `FOODLOGGER_GOALS_ENABLED`, **off by default**. Missing PostgreSQL schema fails closed without changing legacy meal routes. The daily read model uses the current journal rows and goals in one owner-locked transaction, with no duplicate intake store.
- Today shows consumed/target/remaining, a calorie ring and macro bars. The calorie band defaults to inclusive 90–110% and is configurable; protein is met at >=100%. Exact arithmetic preserves threshold boundaries. The 4/4/9 advisory never overwrites user values. Technical finite-number bounds prevent near-zero overflow.
- Unset goals, unlogged days and partial nutrients remain explicit. A known subtotal is not a complete total; partial remaining/percentage are unknown. Logged days say logging completeness is unknown. Water shows a target with intake untracked until P07. No overall full-intake adherence score is invented.
- Existing clock/add/deep links remain. Confirmed meal mutations recompute progress from current journal state. Goal changes share one account store between settings and Today. Optimistic failures restore prior targets visibly; uncertain saves require a successful reload before retry. Stale responses and closed-account saves cannot overwrite newer history or repopulate erased caches.
