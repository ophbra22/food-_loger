# RC04 — editing saved meals

Implemented locally; independent review/final verification pending at this draft. Device UI and full E2E acceptance remain external gates.

## Behavior

The journal detail screen opens `/meal/edit/[id]`. `domain/meal-edit.ts` resolves a component through the existing day-group list, fetches the complete current group, and opens the shared MealAnalysisReview/MealFoodEditor. Legacy groups retain unknown time and scale saved totals rather than querying a changed catalog. Multiple ingredients, quantity, date, time and category reuse the current review flow.

`api/endpoints.ts` wraps existing GET/PATCH with runtime validation, optimistic version and a stable idempotency key. `data/save-draft.ts` persists attempted state before PATCH. An uncertain outcome freezes content and permits only the exact retry; 409/404/422 requires explicit discard/reload, with no automatic POST or version bump. Cancel before sending makes no server mutation. Account/storage fences apply before dispatch and after response.

Pending edits use schemaVersion3 at the current account `draft:v2` key. New readers still accept ordinary version2 drafts; old readers reject version3 instead of accidentally adding a pending edit as a new meal. This is an additive local envelope, not a SQL migration.

`JournalStore.replaceConfirmedGroup` replaces only the edited group, updates both affected days and emits one canonical change event. Library/trends/advice invalidate. Enabled Health subscription and widget lifecycle respond through their existing interfaces. Goals and unrelated meals are preserved.
