# RC03 — basis-correction provenance

Implemented locally; independent review/final verification pending at this draft. Physical/provider/staging gates remain open.

## Behavior and files

`src/foodlogger/domain.py` adds optional BasisCorrection with original NutritionPer100 and FoodReference. Absent metadata is omitted rather than serialized as null, preserving old request digests. `app.py` advertises `basis_correction_provenance`. Existing JSON snapshots retain it: no SQL schema change or migration.

`mobile/src/domain/{canonical,meal-analysis,unified-review,library}.ts` and `storage/account-data.ts` read/retain the metadata. `correctBasis` captures the first source/values, preserves them across g→ml→g, sets manual override and requires renewed confirmation. It does not infer density or change the user's amount automatically. Reference replacement clears correction for the replaced food. `MealFoodEditor` displays original/current basis and original nutrition/source in Hebrew/English. Corrected current source is user-confirmed, not provider-verified.

`api/endpoints.ts` and `data/save-draft.ts` gate new metadata on server support before writing. Round-trips cover draft, canonical meal, private product, recipe, repeat, copy and account export. Historical records without source metadata remain historical/unknown.

## Tests and compatibility

RED→GREEN recorded for first-source retention and UI/capability handling; targeted backend26 and full backend663 passed with9 skips at the RC03 checkpoint; mobile436/85 suites passed there. Final totals in the wave report supersede these intermediate runs. Three real-model smokes remain NOT RUN.

Old payload omission/null normalizes to the same digest; retry does not become a new save. All current canonical writers preserve provenance and fail closed against a server missing the capability. A rollback must retain compatible readers and API support for already persisted data; an arbitrary old writer is not approved merely because the new field is optional.

## Recovery

Stop distributing/entering the new correction UI before downgrading a writer. Keep the compatible reader, capability and stored JSON metadata. No destructive migration or metadata stripping. Mixed-version staging/downgrade replay is still RC16/RC19, not proven by local tests.
